## What changed vs. upstream

1. **`install.py` is not used at all.** It hard-fails on non-aarch64
   (`platform.machine()`), on package versions from `assets/runtime-lock.json`,
   on sha256 of six QNN/ORT binaries, on cores 4–7 being in the affinity mask,
   and it shells out to the host `g++`. None of that belongs in a Yocto image
   build. Everything it did is redistributed as: recipe (fetch/verify/compile/
   install), `qwen35-mkconfig.py` (runtime.json + shims), `qwen35-launch.sh`
   (environment + flock + affinity + exec), `qwen35.service` (unit).
2. **`mkconfig.py` vs `install.py`'s `cfg['paths']` block** — same shape, new
   roots:
   | key | upstream | here |
   |---|---|---|
   | assets (`embedding`, `tokenizer`, `*_model`, `rope`, `tensor_contract`, `advance_plan`, `*_assembly_report`) | `dest/...` from the download dir | `/usr/share/qwen35/<role path>` (role map from `assets/manifest.json`, groups `common`+`2k`) |
   | `frontend_script`, `persistent_stage_worker`, `still_frontend_helper`, `vlm_bundle_helper` | `<install>/…` | `/usr/lib/qwen35/…` (same filenames) |
   | `python` | `<install>/qwen-python` (generated) | `/usr/lib/qwen35/qwen-python` (generated by mkconfig, re-created by launch.sh if missing) |
   | `decoder_engine` | `<install>/engine.sh` (generated) | `/usr/lib/qwen35/engine.sh` (same, incl. `arena_disjoint`) |
   | `scratch_root` | `<install>/scratch` | `/var/lib/qwen35/scratch` (writable, `StateDirectory`) |
   | `metrics_log` | `<install>/logs/requests.jsonl` | `/var/lib/qwen35/logs/requests.jsonl` |
   | `qnn_plugin` / `qnn_backend` | `onnxruntime_qnn.get_library_path()` / `get_qnn_htp_path()` | same call first; falls back to `--qnn-plugin/--qnn-backend`, `QWEN35_QNN_PLUGIN/QWEN35_QNN_HTP`, then a search of `$LIB/qnn`, `$LIB/lib`, `/usr/lib/qwen35/qnn`, `/usr/lib/aarch64-linux-gnu`. It **fails loudly** if nothing is found (no silently wrong placeholder). |
   | `port` | `--port` (default 8000) | `--port` (default 8000) |
   The `onnxruntime_qnn` import is tried first because that is what the board
   uses, but it is *not* importable by the build-host interpreter, which is why
   the override chain exists. The 4K profile is supported by `--profile 4k` as
   well, but only `configs/2k.json` is shipped (decision in the brief).
   `mkconfig.py` also writes `qwen-python` + `engine.sh` next to runtime.json,
   exactly the two files upstream's installer wrote, so `/usr` can be
   read-only at runtime.
3. **`launch.sh` vs upstream `launch.sh` + `qwen-python`** — merged into one
   script (the brief's requirement, and what `files/CLEANUP.md` §3 asks for).
   It keeps `ulimit -Sn 4096`, a single-instance `flock -n` lock and the
   `taskset -c 4-7` pinning, and it exports
   `LD_LIBRARY_PATH` (`/usr/lib/qwen35:/usr/lib/qwen35/qnn:/usr/lib/qwen35/lib`
   + inherited) and `ADSP_LIBRARY_PATH`
   (`$SKEL_DIR;/usr/lib/dsp/adsp;/dsp`, default `$SKEL_DIR=/usr/lib/dsp/cdsp`;
   the DSP-visible directory is chosen so the skel and `libQnnHtp.so` come from
   the same QAIRT release, and the list is `;`-separated because that is the
   only form QNN understands).

   > Board-verified (this supersedes the earlier draft
   > `<qnn>;/usr/lib/runtime/qnn;/usr/lib/rfsa/adsp;/dsp;/usr/lib/dsp/cdsp;/usr/lib/dsp/adsp`):
   > the running server's environment is
   > `ADSP_LIBRARY_PATH=/usr/lib/dsp/cdsp;/usr/lib/dsp/adsp;/dsp`,

   tries to write next to the program; missing assets/engine/config produce an

## Field findings folded into this port (board-verified, 2026-10-23)

The NPU path is proven on the board (genie + llama3.2-1b → "2+2=4"). Four
consequences are baked into the artifacts in this directory:

### 1. `ADSP_LIBRARY_PATH` is `;`-separated, never `:`

A `:` value is read as one long nonexistent directory name; QNN then logs
`Failed to load skel, error: 1002` and `QnnDevice_create 14001` even though the
files are right there. Upstream `install.py` already does `';'.join(dsp)` — it is
copied, not "prettified".

* `qwen35-launch.sh` builds the list by appending `;`-separated entries (with a
dedupe loop, so `QWEN35_SKEL_DIR=/usr/lib/dsp/cdsp` does not appear twice) and
  logs the final value at every start.
* `qwen35.service`'s fallback `Environment=ADSP_LIBRARY_PATH=...` uses `;` too.
* `runtime/2k/qwen_server.py` (unmodified, verbatim) already uses
  `f"{qnn_plugin.parent};/usr/lib/dsp/cdsp;/usr/lib/dsp/adsp;/dsp"` for the
  decoder child — consistent.

### 2. Backend and skel must be the same QAIRT release

The image carries two QAIRT installs:

| path | QAIRT | role |
|---|---|---|
| `/usr/lib/rfsa/adsp/libQnnHtpV68Skel.so` | 2.47.0 | host-side view, historical |
| `/usr/lib/npu-llm/{libQnnHtp.so,libQnnHtpV68Skel.so}` | 2.40.1 | genie / npu-llm stack |

A 2.40 backend loading a 2.47 skel crashes. Therefore **qwen35 takes its whole
QNN set from the `onnxruntime-qnn` 2.3.0 wheel** (one release, pinned by the
recipe) and never borrows from `/usr/lib/npu-llm` or `/usr/lib/rfsa/adsp`.

Guards added:

* `qwen35-launch.sh` greps the embedded `4-part` version string out of
  `libQnnHtp.so` and the resolved `libQnnHtpV68Skel.so`, logs both, and prints a
  loud `ERROR QAIRT version mismatch` when they differ (best effort — a stripped
  `.so` yields no version, in which case only the paths are logged). It also
  warns when `QWEN35_QNN_DIR` resolves into a known foreign install.
* `qwen35-mkconfig.py` warns when `--qnn-plugin/--qnn-backend` (or the fallback
  search) lands under `/usr/lib/npu-llm` or `/usr/lib/rfsa/adsp`.

### 3. The skeleton must be visible to the DSP

The DSP domain sees `/usr/lib/dsp/cdsp` (CDSP) and `/usr/lib/dsp/adsp` (ADSP).
`/usr/lib/rfsa/adsp` is the *host* view and must not be listed. Qwen3.5 HTP runs
on the CDSP (`Effective cdsp_id is: 3`).

So the split the recipes must implement:

```
host side (LD_LIBRARY_PATH)          DSP side (ADSP_LIBRARY_PATH)
/usr/lib/qwen35/qnn/                 /usr/lib/dsp/cdsp/
  libonnxruntime_providers_qnn.so      libQnnHtpV68Skel.so   <- same wheel
  libQnnHtp.so        (backend)
  libQnnHtpV68Stub.so
  libQnnSystem.so
```

`qwen35-launch.sh` defaults `QWEN35_SKEL_DIR=/usr/lib/dsp/cdsp`, exports
`ADSP_LIBRARY_PATH="$SKEL_DIR;/usr/lib/dsp/cdsp;/usr/lib/dsp/adsp;/dsp"`, and
warns if no skel is found in it. The previous `ADSP_LIBRARY_PATH` in this port
listed `/usr/lib/runtime/qnn` and `/usr/lib/rfsa/adsp`; both are gone.

### 4. Verified-good reference invocation (for board-side debugging)

```sh
export ADSP_LIBRARY_PATH='/usr/lib/dsp/cdsp;/dsp'
export LD_LIBRARY_PATH=/usr/lib/npu-llm:/usr/lib
/usr/lib/npu-llm/genie-t2t-run -c model-config.json --prompt '...'
```

That is the *npu-llm* stack (2.40.1) and is not what qwen35 runs, but it is the
known-good baseline for comparing QNN logs. The equivalent shape for qwen35:

```sh
ADSP_LIBRARY_PATH='/usr/lib/dsp/cdsp;/dsp' \
LD_LIBRARY_PATH=/usr/lib/qwen35:/usr/lib/qwen35/qnn:/usr/lib/qwen35/lib \
  /usr/lib/qwen35/qwen35-launch.sh            # or QWEN35_* overrides by hand
```

## Contract for the recipe (bb owner)

Build-time:

```sh
# cross compile the engine (qnn_memory.cpp is #included by qwen_text_engine.cpp
# -- compile ONLY the latter, exactly like install.py did)
$CXX -std=c++20 -O3 -DNDEBUG -pthread \
     -I${S}/native/ort_include \
     ${S}/native/qwen_text_engine.cpp \
     <path>/libonnxruntime.so.1.27.0 \
     -Wl,-rpath,'$ORIGIN/lib' -ldl -o ${D}${libdir}/qwen35/qwen_text_engine
# (-DQWEN_CONTEXT=4096 is only for the 4K profile)

# config + shims
python3 ${S}/qwen35-mkconfig.py --config ${S}/configs/2k.json \
    --assets-root /usr/share/qwen35 --lib-root ${D}${libdir}/qwen35 \
    --state-root /var/lib/qwen35 --port 8000 \
    --qnn-plugin <installed libonnxruntime_qnn*.so> \
    --qnn-backend <installed libQnnHtp.so>
```

Install-time expectations that this port depends on (other workers):

* **QNN set from one wheel, split host/skel.** `/usr/lib/qwen35/qnn/` gets
  `libonnxruntime_providers_qnn.so`, `libQnnHtp.so`, `libQnnHtpV68Stub.so`,
  `libQnnSystem.so`; the same wheel's `libQnnHtpV68Skel.so` must be **copied to
  `/usr/lib/dsp/cdsp/`** (DSP-visible). Do not point either at
  `/usr/lib/npu-llm` or `/usr/lib/rfsa/adsp` — see findings §2/§3.
* **`/usr/lib/qwen35/lib/libonnxruntime.so.1` → `libonnxruntime.so.1.27.0`**
  symlink (the wheel ships only the versioned file; the ELF SONAME is
  `libonnxruntime.so.1`, and `qwen_text_engine` links the versioned path).
* QNN libs reachable at runtime: `libonnxruntime_providers_qnn.so`,
  `libQnnHtp.so`, `libQnnSystem.so`, `libQnnHtpV68Stub.so`,
  `libQnnHtpV68Skel.so` (from `onnxruntime-qnn` 2.3.0). Putting them in
  `/usr/lib/qwen35/qnn` matches `QWEN35_QNN_DIR`, the launcher's
  `LD_LIBRARY_PATH`/`ADSP_LIBRARY_PATH`, and the fallback search in mkconfig.
* Python modules on the target: `numpy` (Debian rootfs, cp313), `tokenizers`
  0.22.2 (needed at server start, abi3 wheel), `onnxruntime` 1.27.0,
  `onnxruntime-qnn` 2.3.0. Nothing else from upstream's
  `requirements-device.txt` is shipped: `onnx`, `flatbuffers`, `protobuf`,
  `sympy`, `ml_dtypes`, `coloredlogs`, `humanfriendly` and `pillow` are either
  required only by `chunk_prefill.py` (not shipped) or only declared in wheel
  metadata without being imported. See `../onnxruntime/README-DEPS.md` §3.
  `requirements-device.txt` / `assets/runtime-lock.json`.
* `taskset` (util-linux) and `flock` (util-linux) at runtime; `ulimit -Sn 4096`
  matters because each in-flight chunk holds many fd's.

## Open risks / notes for whoever runs the board

1. **Vision assets are still required.** `qwen_server.py` hard-requires
   `vision_patch_model`, `vision_body_model`, `vision_merger_model` (module
   import + `is_file()` validation), so runtime.json points at
   `/usr/share/qwen35/models/vision/*_ctx.onnx`. Either the model recipe ships
   the 3 vision pairs (+ `_qnn.bin`, 167 MB) or `qwen_server.py` must be
   patched — the brief said "no vision", the code says otherwise. Cheapest
   path: ship them; dropping the files without patching the server means the
   unit refuses to start.
2. **`qwen_server.py` rebuilds `ADSP_LIBRARY_PATH` for the decoder child** as
   `paths['qnn_plugin'].parent;/usr/lib/dsp/cdsp;/usr/lib/dsp/adsp;/dsp`
   (semicolons, and the DSP dirs are correct — so the `;` rule holds on the
   board-verified path too). Two consequences: (a) if the EP directory ever
   holds a *skel*, that copy wins — keep only the host libs in
   `/usr/lib/qwen35/qnn` and the skel in `/usr/lib/dsp/cdsp`; (b) the plugin
   directory must be the wheel's, otherwise the 2.40/2.47 mismatch comes back.
3. Asset sizes: `common/embedding_fp32.npy` is **1017118848 B** (the task brief
   said 1017011848 — the manifest and the downloaded file agree on the former;
   use the manifest sha256/size when writing `SRC_URI`).
4. `HOST` stays `127.0.0.1`; the API is loopback-only by design
   (`qwen_server.py` rejects anything else). Exposing it needs a proxy.
5. `files/model/` (old CPU ONNX) is git-ignored and untouched.

## Board run: what only the PI H1 could show

First full boot after flashing (`qwen35.service` enabled, firmware
`6.6.116-qli-1.7-ver.1.1`, Debian 13, CPython 3.13). Everything above held;
these four things did not, and are now fixed in the recipe rather than
documented as "known issues":

1. **`/usr/lib/qwen35/scratch` must be a symlink into the state root.**
   `stage_worker.py:108` derives the only directory it will write its vision
   warmup into as `Path(__file__).resolve().parent / "scratch"` and aborts with
   `ValueError: warmup must stay inside the new layered scratch directory`
   otherwise, while `qwen_server.py` passes `paths["scratch_root"]`
   (`/var/lib/qwen35/scratch`) as `--vision-warmup-dir`. The service therefore
   restart-looped until the link existed. `do_install` now creates it (a
   symlink, so the shipped `.py` files stay byte-identical to upstream),
   `qwen35-verify.sh` check 5 asserts it resolves to `$STATE_DIR/scratch`.
2. **`${localstatedir}` is `/var`, not `/var/lib`.** `QWEN35_STATEDIR` was
   `/var/qwen35` while the unit's `StateDirectory=qwen35` +
   `QWEN35_STATE=/var/lib/qwen35` said otherwise, so `runtime.json` pointed the
   scratch root and the metrics log at a directory systemd never creates and
   `ReadWritePaths=` does not cover. Now `${localstatedir}/lib/qwen35`.
3. **The CDSP does not always come up on the first boot after a flash.**
   `qcom_q6v5_pas a300000.remoteproc: start timed out` → `-110` →
   `remoteproc3` offline → no `/dev/fastrpc-cdsp` → `cdsprpcd` restart loop →
   QNN `open_device_node failed for domain ID 3`. `qwen35-launch.sh` now looks
   up `a300000.remoteproc` by name, writes `start` to its `state` when the node
   is absent, and waits up to 15 s for `/dev/fastrpc-cdsp`; on the next boot
   the DSP had come up by itself in 12 s, so this is a race, not a
   configuration error. Verified by stopping the rproc by hand and starting the
   unit: `CDSP is offline, retrying the a300000.remoteproc start` →
   `CDSP ready` → `ready:true` in ~3 s.
   **One attempt is still not enough** (see the follow-up section below): each
   `echo start` blocks for the whole 5 s handshake and then leaves the rproc
   offline again, so the 15 s poll gave up exactly one attempt too early on the
   real first boot. The launcher now retries until `/dev/fastrpc-cdsp` appears
   or `QWEN35_CDSP_TIMEOUT` (default 60 s) expires.
4. **Image input needs Pillow.** `request_frontend.py:121` imports it unguarded
   inside `preprocess_image()`; `image_frontend.py`'s `try/except` is the CLI
   path only. Without it the endpoint returns 500
   `ModuleNotFoundError: No module named 'PIL'`. Shipped as its own
   self-contained cp313 wheel (`../onnxruntime/pillow_11.3.0.bb`); with it, a
   96x96 PNG answered correctly with `mode=image`, `vision_run_seconds=1.22`.

Measured on the board (`qwen35-verify.sh`, full pass): **PASS 57 / FAIL 0 /
WARN 8**, `17*23=391` correct, decode 6.95/6.95/6.99 tok/s over three runs
(1.006x spread, TTFT ~3.8 s), `MemoryCurrent` 341 MiB of a 5 GiB
`MemoryMax`, hottest zone 51 °C, `NRestarts=0`. The 8 warnings are the Radxa
7.4 tok/s reference, two `fastrpc unmmap … ERROR` teardown lines, the volatile

## Follow-up board run: on-demand start, NPU-only gate, CDSP retries

Second full build + flash of the same tree (`buildall`, no hand patching on the
board). The unit came up `enabled` and then died on its first start, which
turned into three fixes.

1. **The server must not start at boot.** It pins CPU 4-7, holds ~490 MB RSS and
   owns the whole NPU context, so a board that never uses the model was still
   paying for it. `SYSTEMD_AUTO_ENABLE` is now `disable` and the image ships the
   unit inactive; `npu-chat` starts it when the user selects qwen3.5 and stops
   it again when they switch away (both paths already existed). `[Install]`
   stays, so `systemctl enable qwen35` still opts back in.
   Consequence that had to be fixed with it: `npu-chat`'s `qwen35_installed()`
   used to fall back to `systemctl is-enabled qwen35` after the `QWEN35_OK`
   marker, so a disabled unit would have hidden qwen3.5 from the model list
   entirely. It now gates on the install being complete (launcher + every
   asset) and nothing else, because `start_qwen35()` waits for the server
   anyway. Verified on the board with the unit stopped and disabled:
   `qwen35_installed() == True`, `qwen35_up() == False`,
   `start_qwen35() -> OK in 7.1 s`.
2. **CDSP bring-up needed more than one attempt.** The previous form wrote
   `start` once and polled 15 s. A failing `echo start` blocks ~8 s (the PAS
   handshake has a 5 s timeout) and leaves the rproc offline, so the first boot
   after a flash consumed the entire budget in one attempt and the unit exited
   1; systemd's `Restart=always` then brought it up on the second try
   (`NRestarts=1`). The launcher now loops on a wall-clock deadline
   (`QWEN35_CDSP_TIMEOUT`, default 60 s), re-writing `start` whenever the state
   is not `running` and polling the node in 1 s steps, and logs every attempt.
   Exercised against a stub rproc: 3 attempts in a 15 s budget, `ready` after
   the node appeared at t=3 s, and no write at all when the node already
   existed.
3. **`/run/qwen35.ok` is now actually written.** `qwen35-launch.sh` spawns a
   child that polls `GET /v1/models` and drops the marker on the first 200
   (`QWEN35_READY_TIMEOUT`, default 120 s); `ExecStopPost` removes it. Before
   this, `npu-chat`'s `QWEN35_OK` path could never fire and verify check 6
   warned about a design that did not exist.
4. **The `/health` NPU-only assertion was wrong, not the board.** It looked for
   the string `npu_qnn_htp`, which the server never emits; the real report is
   `backend.{vision,layers_0_19,layers_20_23,decode}` plus
   `persistent_stages.vision_*_assigned_nodes`. The check now parses the JSON and
   asserts structure: all four placements name QNN and HTP and none names the
   CPU, `cpu_fallback_for_npu_partitions=false`,
   `language_prefill_full24_npu=true`, `fallback_disabled=true`,
   `only_qnn_provider_in_every_profile=true`, every
   `vision_cpu_assigned_nodes` is 0 and every `vision_qnn_assigned_nodes` is
   > 0. Negative-tested by moving `decode` to `CPUExecutionProvider`: the check
   fails and exits 1.
5. **`qwen35-journald.conf` was a dead file** (not in `SRC_URI`, referenced by a
   `JOURNAL_SETUP.md` that never existed). It ships as
   `/usr/share/doc/qwen35-npu/journald.conf.example` now; making the journal
   persistent is a whole-system trade-off this package deliberately does not
   flip, so verify only points at the example.

Board state after the fixes: `systemctl is-enabled qwen35` → `disabled`,
`is-active` → `inactive`, no `/run/qwen35.ok`, no `qwen_server.py` after a
reboot (baseline 1248 MB used of 7357 MB). `systemctl start qwen35` →
`active`, `NRestarts=0`, marker written 10 s after exec. Full
`qwen35-verify.sh`: **PASS 61 / FAIL 0 / WARN 6**, `17*23=391`, decode
6.95/6.95/6.96 tok/s, `MemoryCurrent` 318 MiB, hottest zone 50 °C. The 6
